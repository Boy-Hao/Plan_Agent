# 云端智能体平台建设方案

> 参考对象：`https://xpd-agent-test.x-peng.com/`（小鹏 XPD「云端智能体平台」，测试环境，前端版本 `1.6.11-test-2231012`）
> 文档定位：从 0 到 1 建设一个「企业级云端智能体平台」的产品、技术、资源与实施总方案。
> 编写原则：**外部可观测事实** 与 **合理推断/建议** 严格区分；不复制参考系统代码，不记录任何密钥。

---

## 0. 一页结论

参考系统不是「一个聊天页面」，而是一个**企业 AI 应用操作系统**，由六层组成：

1. **入口层**：Web 工作台、H5、飞书机器人、A2A、OpenAPI、嵌入式 Bridge。
2. **会话层**：Agent 发现、会话、SSE 流式对话、附件、产物、反馈、通知。
3. **编排层**：LangChain DeepAgents 多 Agent 编排、Skills 工具、MCP、子 Agent、任务计划、调用链。
4. **资源层**：模型配置、能力注册表、配额池、沙箱配置、Skills 仓库、提示词模板、变量、引用源。
5. **治理层**：SSO、RBAC、资源 ACL、API Key、权限点审计、OSS 治理、用量与成本。
6. **集成层**：飞书、GitLab、A2A、数据网页、图表、定时调度、Webhook。

建设这样一套系统，真正的难点不是「接一个大模型」，而是：

- **权限与数据范围**：功能权限、资源归属、协作者、数据可见性、审计授权要能组合。
- **流式会话的可靠性**：断线续传、刷新恢复、取消、并发轮次、多端一致性。
- **AI 资源的可控性**：模型能力差异、参数覆盖、TPM 配额、成本核算、故障降级。
- **执行环境的安全性**：代码沙箱隔离、Git 凭证租约、网络与密钥边界。
- **组织级运营**：Skill 治理、效果评估、用量分析、反馈闭环、灰度发布。

**建议路线**：先做「模块化单体 + 独立 Agent Runtime + 独立 Sandbox Worker」，12 周交付 MVP，24 周达到可推广的 GA；不要一开始拆微服务。

## 3. 推荐技术栈（新建系统）

| 层 | 推荐选型 | 说明 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite + React Router + TanStack Query + Zustand + Ant Design 5 + ECharts + react-markdown/Shiki | 与参考系统同代际；管理端表单多，Ant Design 效率最高 |
| 流式 | 原生 `EventSource`/`fetch` + SSE 协议封装；NDJSON 作为备选 | 需要 `Last-Event-ID`、心跳、重连、取消 |
| 后端 | Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic | 与 LangChain 生态一致；自动 OpenAPI |
| 数据库 | MySQL 8.0（utf8mb4，软删除，逻辑外键） | 参考系统使用 MySQL 语义（`utf8mb4_bin`） |
| 缓存/流 | Redis 7（Cluster 或主从 + Sentinel） | 会话、SSE ring buffer、配额桶、分布式锁、权限缓存 |
| 队列 | Redis Streams / ARQ 起步；规模上来后 Kafka | 沙箱任务、飞书推送、盘点、导出 |
| Agent | LangGraph / DeepAgents + 自研 Tool/Skill 协议 + MCP + A2A | 复杂编排用图，简单场景用单 Agent |
| 生成式 UI | OpenUI 或自研「卡片/组件白名单 + JSON Schema」 | 不要让模型直接输出任意 HTML |
| 沙箱 | 自建 E2B（Firecracker）或 K8s Job + gVisor/Kata | 代码执行必须强隔离；先做单租户池 |
| 对象存储 | S3 兼容（阿里云 OSS / MinIO） | 版本、生命周期、预签名 URL |
| 可观测 | OpenTelemetry + Prometheus + Grafana + Loki + Tempo/Jaeger + Sentry | 指标、日志、链路、前端错误 |
| 特性开关 | Unleash / 自研 JSON Flags | 参考系统的六波灰度值得借鉴 |
| 部署 | Docker + Kubernetes + Helm + GitLab CI/Argo CD | 多环境、蓝绿/金丝雀 |
| 密钥 | Vault / K8s Secrets + KMS | 应用层 Fernet/AES-GCM 二次加密 |

## 6. 五个必须先定的决策

1. **单租户还是多租户**：参考系统是单公司多用户。若要做 SaaS，`tenant_id` 必须从第一天进入所有表与缓存键。
2. **Agent 编排框架**：LangGraph/DeepAgents 还是自研状态机。建议「LangGraph 起步 + 自研协议层」，避免被框架锁死。
3. **沙箱方案**：E2B 自建、K8s Job、还是云厂商托管。建议先托管验证，再自建降本。
4. **模型供给**：统一网关（LiteLLM/自研）还是各 Provider 直连。建议统一网关，否则配额、计费、降级会失控。
5. **权限模型**：只做 RBAC 还是 RBAC + 资源 ACL + 审计授权。参考系统证明，企业落地必须三者齐全。

## 7. 使用建议

- 把本套文档当作「决策底稿」：每份文档末尾都有验收标准与待定项，评审时逐项打勾。
- 先做 **MVP 闭环**：登录 → 选 Agent → 流式对话 → 用 1 个 Skill → 留历史 → 管理员可配置。
- 不要在第一版做：微服务拆分、复杂多 Agent 自治、全量 OSS 治理、完整权限审计工作流。这些放 P2/P3。
- 所有外部集成都要有 **Mock 适配器**，否则开发和测试会被飞书/GitLab 环境卡死。
