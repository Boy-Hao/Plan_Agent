# 方案主次编排

> 这套文档不再按「功能清单」平铺，而是按**主次/生死线**重新编排：
> 先做什么、为什么、做到什么程度、什么可以后置、各主线如何并行与验收。

---

## 1. 为什么要主次编排

平台有 60+ 文档、400+ 接口、几十种模式。如果按功能平铺，团队会：

- 同时开太多战线，集成期才发现主线不稳；
- 把「增强功能」当「生死线」，把「基础一致性」留到最后；
- 优化做了一堆，但用户核心任务仍不稳。

**主次编排的原则**：
1. **先保命**：身份/权限/租户、运行时/SSE、模型/配额、Skill/MCP 工具链。
2. **再保稳**：沙箱、文件/数据、管理端、可观测。
3. **再做广**：飞书/GitLab/A2A、多 Agent、治理。
4. **最后做优**：性能、成本、评测、缓存、路由。
5. **按依赖排序**，不按「想做」排序。

## 2. 四条线

| 线 | 定位 | 失败后果 | 文档 |
|---|---|---|---|
| **第一主线（生死线）** | 没有它系统不成立 | 不可用/不安全/不可控 | 01–04 |
| **第二主线（支撑线）** | 没有它不能生产 | 不可运维/数据丢失 | 05–06 |
| **第三主线（增强线）** | 没有它不能规模化 | 采用率低/治理缺失 | 07 |
| **持续线（优化线）** | 没有它不可持续 | 贵/慢/退化 | 08 |

## 5. 主次判定规则

| 问题 | 判定 |
|---|---|
| 没有它，用户能否完成核心任务？ | 不能 → 生死线 |
| 没有它，是否可能数据泄露/越权？ | 是 → 生死线 |
| 没有它，能否上线但不可运维？ | 不能运维 → 支撑线 |
| 没有它，能否上线但采用率低？ | 是 → 增强线 |
| 没有它，能否上线但越来越贵/慢？ | 是 → 优化线 |
| 只是「看起来酷」？ | 后置 |

---

## 6. 三个硬规则

1. **生死线未达标，不启动增强线**（不并行开飞书/多 Agent）。
2. **支撑线未达标，不扩用户规模**（不上 1000 DAU）。
3. **优化线必须在评测护栏内**（质量不降才上线）。
