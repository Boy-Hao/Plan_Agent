# 24 架构评审与差距分析

## 1. 评审方法

采用 **ATAM + 质量属性场景 + 风险热力图**：

1. 明确业务驱动（多入口、强权限、可控成本、可审计）。
2. 列出质量属性（可用性、性能、安全、可修改性、可运维性、成本）。
3. 对每个属性写可度量场景（刺激 → 响应 → 度量）。
4. 识别架构决策、敏感点、权衡点、风险。
5. 输出差距、优先级、责任人、验证方式。

**评审输入**：主文档 01–23、参考系统拆解、MVP 范围、团队规模。
**评审输出**：本文件 + ADR + 行动项。

## 2. 现状评分（架构师视角）

| 维度 | 现状 | 评分（1–5） | 说明 |
|---|---|---|---|
| 业务分层 | 六层能力地图清晰 | 4 | 产品/技术/治理分层合理 |
| 模块边界 | 有模块划分，但缺依赖规则 | 3 | 易退化为「大泥球」 |
| 运行时正确性 | SSE/取消/续传有设计 | 3.5 | 缺事件一致性/幂等细节 |
| 数据架构 | 有表清单，缺一致性与分区 | 3 | 10x 后消息/用量会痛 |
| 可扩展性 | 有水平扩展方向 | 3 | 缺容量模型与瓶颈量化 |
| 高可用 | 有备份/容灾原则 | 2.5 | 缺故障矩阵与降级等级 |
| 安全 | 有威胁模型与清单 | 3.5 | 租户隔离/供应链需深化 |
| 可运维性 | 有指标/SLO | 3 | 缺 Runbook 与演练闭环 |
| 成本 | 有估算与控制 | 3 | 缺单位经济模型 |
| 可演进性 | 有单体起步策略 | 3 | 缺拆分触发条件 |

**结论**：方案「可开工」，但若要支撑 1 万 DAU / 多团队 / 强合规，需要补 7 个架构缺口。

## 3. 七个关键差距

### G-01 租户隔离只停留在字段层

**现状**：建议所有表加 `tenant_id`，但未定义网关解析、缓存键、OSS 路径、审计、模型配额的强制隔离。
**风险**：跨租户数据泄露；缓存/对象存储串租户；配额被邻居打爆。
**补齐**：
- 网关解析租户（域名/Header/Token claim），注入不可伪造的 `TenantContext`。
- 所有 repository 强制带 `tenant_id`；ORM 层做默认过滤，禁止裸 SQL。
- Redis key、OSS 前缀、日志字段、指标标签全带租户。
- 跨租户访问测试纳入 CI（见 30）。
**优先级**：P0（若确定 SaaS）；P1（若单租户但未来可能 SaaS）。

### G-02 Runtime 与 Control Plane 的数据边界不清

**现状**：Runtime 需要读 Agent/模型/技能配置，可能直接访问业务库。
**风险**：Runtime 写入控制面数据、连接池争用、故障扩散。
**补齐**：
- Runtime 只读配置（只读副本/缓存），只写会话/消息/用量（独立 schema 或独立库）。
- 控制面与 Runtime 使用不同 DB 账号/连接池；禁止跨域事务。
- 配置变更通过事件/缓存失效通知 Runtime，而不是 Runtime 轮询全表。
**优先级**：P0。

### G-03 会话/SSE/用量缺少一致性模型

**现状**：消息、SSE 事件、用量、审计分别写，未定义失败补偿。
**风险**：消息显示成功但用量丢失；SSE 断线后状态不一致；重复计费。
**补齐**：
- 引入 **Outbox**：消息/用量/审计与业务状态同事务写 outbox，异步投递。
- SSE 事件带 `event_id/seq`，至少一次 + 去重；ring buffer 可重放。
- 用量以「LLM 调用」为最小幂等单元，唯一键 `(message_id, call_seq)`。
**优先级**：P0。

### G-04 配额池的分布式正确性未定义

**现状**：令牌桶算法合理，但未说明 Redis 原子性、时钟、缓存折算、对账。
**风险**：超发导致供应商账单飙升；拒绝率抖动；多实例时钟不一致。
**补齐**：
- Lua 脚本原子「补充 + 扣减 + 排队」；使用 Redis 服务端时间。
- 每池一个分片键，避免热 key；大池按 `pool_id + shard` 分桶。
- 定时快照 + 与供应商账单对账；超发阈值告警。
- OBSERVE 模式记录「本应拒绝」用于校准。
**优先级**：P0（若配额是成本控制手段）。

### G-05 沙箱的安全与供给未形成闭环

**现状**：E2B 语义、生命周期、Git 租约都有，但缺镜像供应链、网络策略、容量与逃逸演练。
**风险**：恶意代码逃逸；镜像被投毒；高峰期创建失败；成本失控。
**补齐**：
- 镜像签名 + 扫描 + 固定 digest；模板最小化。
- 沙箱节点独立节点池/账号/网络策略；默认拒绝出站。
- 预热池 + 排队 + 降级（只读工具）；容量告警。
- 每季度逃逸演练；漏洞补丁 SLA ≤ 7 天。
**优先级**：P0（若开放代码执行）；P1（若只读工具）。

### G-06 可观测性缺少「会话级」闭环

**现状**：有指标/日志/Trace，但未定义如何从用户投诉定位到一次对话。
**风险**：排障靠猜；模型/工具问题无法归因；SLO 无法兑现。
**补齐**：
- 全链路 `request_id → session_id → message_id → llm_call/tool_call`。
- 前端错误上报带 `request_id`；客服可输入会话 ID 查 Trace。
- 每轮对话记录「阶段耗时」（排队/上下文/LLM/工具/持久化）。
- 失败样本自动进 badcase 库。
**优先级**：P1。

### G-07 演进路径缺少「拆分触发条件」

**现状**：建议模块化单体，但未定义何时拆、按什么拆。
**风险**：过早拆分增加复杂度；过晚拆分导致耦合固化。
**补齐**：
- 定义触发器：团队规模、部署频率、P95、DB 写放大、故障爆炸半径。
- 拆分顺序：Runtime → Sandbox → Integration → Analytics。
- 每次拆分前先做「接缝」：事件、接口、独立 schema。
**优先级**：P1。

## 4. 10x 压力下先崩什么

| 排名 | 组件 | 10x 现象 | 根因 | 先手 |
|---|---|---|---|---|
| 1 | MySQL 消息/用量写入 | 写放大、慢查询、连接耗尽 | 每 token 写库、缺分区 | 批量写 + 按月分区 + 归档 |
| 2 | Redis 热 key | 配额/会话锁延迟飙升 | 单 pool/session key | 分片、本地缓存、Lua 优化 |
| 3 | SSE 连接内存 | 单实例连接数上限 | 每连接缓冲/心跳 | 独立网关、批量合并、背压 |
| 4 | 模型 TPM | 429、排队、体验抖动 | 供应商限额 | 多供应商、配额池、降级 |
| 5 | 沙箱供给 | 创建排队、超时 | 节点/镜像/调度 | 预热池、自动扩缩、共享池 |
| 6 | 上下文组装 | 首 token 变慢 | 历史/引用源过大 | 摘要、裁剪、缓存 |
| 7 | 审计/日志 | 存储成本、查询慢 | 全量长保留 | 采样、分层、归档 |

## 8. 评审结论

- **通过（有条件）**：可以按 12 周 MVP 开工。
- **条件**：P0 行动项（A-01~A-05）必须在 M1 前完成设计，M2 前完成验证。
- **不建议**：在 MVP 阶段引入多租户 SaaS、微服务、全量权限审计；这些会显著增加复杂度。
- **下次评审**：M2（第 20 周）与 M4（第 28 周），重点看容量、故障、成本、安全。
