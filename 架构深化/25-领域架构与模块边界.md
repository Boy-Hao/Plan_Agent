# 25 领域架构与模块边界

## 1. 为什么要分域

平台功能多、团队多、变化快。如果不划边界，会出现：

- 所有代码都写进 `services/`，模块互相 import；
- 改一个模型字段，牵动会话/计费/审计；
- 团队抢同一张表，发布互相阻塞；
- 无法判断哪些能力可以独立扩展/拆分。

**目标**：用 DDD 的限界上下文（Bounded Context）划出「高内聚、低耦合」的模块，并定义依赖规则与团队归属。

## 3. 上下文职责与数据归属

| 上下文 | 职责 | 拥有的数据 | 不负责 |
|---|---|---|---|
| Identity & Access | 身份、角色、权限、租户、API Key、审计 | sys_user/role/permission、api_key、audit_log | Agent 业务、会话内容 |
| Agent Catalog | Agent 定义、绑定、模板、变量、引用源、卡片 | agent、agent_* | 运行时状态、模型密钥 |
| Skill Registry | Skill 包、版本、分类、评估、治理、共享 | skill、skill_version、personal_skill | Agent 绑定关系（由 Catalog 引用） |
| Conversation & Runtime | 会话、消息、轮次、SSE、任务计划、Trace | session、message、task_plan、trace | 模型配置、沙箱实例 |
| Model Gateway | Provider、模型配置、能力、配额、计费 | llm_config、quota_pool、usage_llm_call | 会话内容、Agent 提示词 |
| Execution | 沙箱配置、实例、任务、Git 租约 | sandbox_*、git_lease | Agent/会话决策 |
| Integration | 飞书、GitLab、A2A、Webhook | feishu_*、gitlab_*、a2a_* | 核心业务状态 |
| Governance & Analytics | 审计、用量聚合、成本、OSS 治理、反馈 | audit、usage_agg、feedback、oss_* | 实时对话 |

**规则**：一个数据只属于一个上下文；其他上下文只能通过 ID 引用或 API/事件读取，禁止跨上下文 JOIN 写库。

## 4. 上下文映射（Context Map）

| 上游 → 下游 | 关系 | 说明 |
|---|---|---|
| Identity → 所有 | 共享内核/上游 | 所有请求携带 TenantContext/UserContext |
| Agent Catalog → Conversation | 客户-供应商 | Runtime 读取 Agent 配置快照 |
| Skill Registry → Agent Catalog | 客户-供应商 | Agent 绑定 Skill ID/版本 |
| Model Gateway → Conversation | 客户-供应商 | Runtime 通过网关调用模型 |
| Conversation → Execution | 客户-供应商 | Runtime 请求沙箱任务 |
| Conversation → Governance | 发布-订阅 | 消息/用量/审计事件 |
| Integration → Conversation | 防腐层 | 飞书/GitLab 消息转换为内部命令 |
| Integration → Execution | 防腐层 | GitLab token/MR 适配 |

**防腐层（ACL）**：飞书、GitLab、LLM、OSS、E2B 都必须有独立适配器，领域层不出现厂商 SDK 类型。

## 5. 聚合与不变量

### Agent 聚合

- 根：`Agent`
- 不变量：
  - 名称在租户内唯一（软删范围）。
  - owner 必须存在且有创建权限。
  - 绑定 Skill/子 Agent/模型必须存在且可见。
  - 删除前必须展示影响（会话/调度/子 Agent）。
- 生命周期：draft → active → disabled → deleted。

### Skill 聚合

- 根：`Skill`，实体：`SkillVersion`、`SkillFile`。
- 不变量：
  - 版本不可变；current_version 指向已存在版本。
  - 包路径不允许穿越；文件哈希与 manifest 一致。
  - 删除需先解绑或标记不可用。
- 生命周期：uploaded → evaluated → published → deprecated → deleted。

### Session 聚合

- 根：`Session`，实体：`Message`、`Turn`。
- 不变量：
  - 同一会话同一时刻最多一个活跃轮。
  - 消息按 `seq` 单调；`msg_end` 必达。
  - 用户只能访问自己的会话（管理员按范围）。
- 生命周期：active → archived → deleted。

### QuotaPool 聚合

- 根：`QuotaPool`，实体：`Snapshot`、`Change`。
- 不变量：
  - 模式切换必须带 `expected_config_version` + 原因。
  - ENFORCE 前参数必须确认。
  - 归档后不可绑定新配置。
- 生命周期：draft → confirmed → OBSERVE → ENFORCE → archived。

### SandboxBinding 聚合

- 根：`SandboxBinding`，实体：`SandboxInstance`、`Task`。
- 不变量：
  - 一个会话在一个作用域内最多一个绑定。
  - 删除/重置必须可预览影响。
  - 任务不能跨绑定执行。

## 6. 模块依赖规则

### 允许

```
api → application(services) → domain
application → repositories / integrations
repositories → domain
integrations → domain (仅 DTO/端口)
```

### 禁止

- domain 依赖 FastAPI/SQLAlchemy/厂商 SDK。
- repository 调用 service。
- 上下文 A 直接写上下文 B 的表。
- 前端直接调用外部厂商 API（除公开 OAuth 跳转）。
- 跨上下文共享可变实体。

### 强制手段

- Python：`import-linter` 定义 layers/forbidden。
- 前端：ESLint `no-restricted-imports` 限制 `features/*` 互相引用。
- CI：架构测试失败即阻断合并。

## 7. 目录映射（后端）

```
app/
  contexts/
    identity/      (api, application, domain, infra)
    agent/         (api, application, domain, infra)
    skill/         (api, application, domain, infra)
    conversation/  (api, application, domain, infra)
    model/         (api, application, domain, infra)
    execution/     (api, application, domain, infra)
    integration/   (api, application, domain, infra)
    governance/    (api, application, domain, infra)
  shared/          (tenant, auth, errors, events, outbox)
```

**每个上下文内部**：`api` 只做协议转换；`application` 编排；`domain` 规则；`infra` 实现端口。
**shared 只放稳定原语**，禁止放业务逻辑。

## 8. 团队拓扑

| 团队 | 类型 | 负责上下文 | 关键指标 |
|---|---|---|---|
| Agent & Chat | Stream-aligned | Agent Catalog、Conversation | 首 token、任务完成率 |
| AI Platform | Platform | Model Gateway、Runtime 框架 | 模型可用性、成本 |
| Execution | Platform | Execution/Sandbox | 创建成功率、隔离 |
| Integrations | Stream-aligned | Integration | 飞书/GitLab 成功率 |
| Trust & Governance | Enabling/Complicated | Identity、Governance | 越权 0、审计覆盖 |
| Web Experience | Stream-aligned | 前端工作台/管理端 | 首屏、交互 |
| SRE | Platform | 部署/可观测/容量 | SLO、MTTR |

**约定**：每个上下文有单一 Owner；跨上下文变更走 RFC/ADR；共享库由 Platform 团队维护。

## 9. 拆分触发条件

| 信号 | 阈值 | 动作 |
|---|---|---|
| 团队规模 | > 30 人 | 按上下文拆服务 |
| 部署冲突 | 每周 > 3 次互相阻塞 | 拆独立部署单元 |
| Runtime 负载 | 与控制面资源争用 | 先拆 Runtime（已拆） |
| 沙箱规模 | 独立节点池 > 50 节点 | 拆 Execution 服务 |
| 集成变更频率 | 每周 > 2 次 | 拆 Integration |
| 报表压力 | 分析查询影响交易 | 拆 Analytics/读模型 |
| 故障爆炸半径 | 单模块故障影响全站 | 隔离部署/降级 |

**拆分顺序**：Runtime → Execution → Integration → Analytics → Identity（最后，因全局依赖）。

## 10. 反模式清单

| 反模式 | 表现 | 纠正 |
|---|---|---|
| 共享数据库 | 多上下文读写同表 | 按上下文拆 schema/表 |
| 贫血领域 | service 里全是 SQL | 规则下沉 domain |
| 万能 service | 一个 service 几千行 | 按用例拆 |
| 事件滥用 | 所有调用都发事件 | 只在跨上下文/异步用 |
| 过度拆分 | 10 人团队 20 个服务 | 模块化单体 |
| 前端直连厂商 | 前端调飞书/GitLab | 后端适配器 |
| 隐式租户 | 忘记 tenant_id | 中间件 + 测试 |

## 11. 验收标准

- [ ] 每个上下文有职责、数据归属、Owner。
- [ ] 模块依赖规则进入 CI，循环依赖为 0。
- [ ] 聚合不变量有单元测试。
- [ ] 跨上下文只通过 API/事件，不共享表。
- [ ] 拆分触发条件明确，接缝（事件/接口/schema）预留。
- [ ] 团队拓扑与上下文映射一致。
