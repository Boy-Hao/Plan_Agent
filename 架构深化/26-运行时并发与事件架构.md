# 26 运行时并发与事件架构

## 1. 问题定义

一轮对话不是一次 HTTP 请求，而是：

- 一个**长事务**（LLM 流 + 工具 + 子 Agent + 持久化）；
- 一个**状态机**（排队、运行、等待、完成、取消、失败）；
- 一个**事件流**（SSE 给前端，内部事件给用量/审计/通知）；
- 一个**并发单元**（同一会话不能有两个活跃轮）。

如果只按「请求-响应」设计，会出现：重复消息、丢 token、取消不生效、用量重复、刷新后状态错乱。

## 2. Turn 状态机

```
                 ┌──────────┐
   client msg →  │ received │
                 └────┬─────┘
                      │ acquire lock
                 ┌────▼─────┐
                 │  queued  │ (await quota/model)
                 └────┬─────┘
                      │
                 ┌────▼─────┐
                 │ running  │
                 └─┬──┬──┬──┘
        LLM stream │  │  │ tool call
                   │  │  └──────────────┐
                   │  │                 ▼
                   │  │          ┌─────────────┐
                   │  │          │ tool_wait   │
                   │  │          └──────┬──────┘
                   │  │                 │ tool end
                   │  └─────────────────┘
                   │
        ┌──────────▼──────────┐
        │ completed / cancelled│
        │ / failed             │
        └─────────────────────┘
```

**规则**
- 状态只能前进，不能回退；终态不可变。
- 每次状态变更写 `turn_event`（审计/恢复）。
- `cancelled` 是终态；已生成内容保留。
- `failed` 记录错误码/可重试标记。

## 3. 会话锁与并发

### 3.1 锁

```
SET t:{tenant}:lock:session:{sid} <turn_id> NX PX 30000
```

- 锁值 = `turn_id`（fencing token），续租时校验值。
- 锁 TTL 30s；运行中每 10s 续租。
- 超时未续租 → 其他请求可抢占；旧 turn 的写入必须校验 fencing token，防止「僵尸写入」。
- 锁释放用 Lua 比较值后删除，避免误删他人锁。

### 3.2 并发策略

| 场景 | 策略 |
|---|---|
| 同一会话并发发消息 | 第二个返回 409/排队，前端提示 |
| 多标签页 | 服务端活跃轮为准；非发起页只读 |
| 多端（Web/飞书） | 同一会话共享；以 `active_turn` 为准 |
| 用户取消后立刻重发 | 等 `msg_end` 释放锁，或强制取消并等待 |

### 3.3 幂等

- 客户端生成 `client_message_id`（UUID），随请求发送。
- 服务端唯一键 `(tenant, session_id, client_message_id)`；重复请求返回同一 `turn_id`。
- `cancel`/`pause`/`resume` 天然幂等。
- 工具执行用 `(turn_id, tool_call_id)` 幂等；外部副作用（发消息/提 MR）需业务幂等键。

## 4. 事件模型

### 4.1 事件分类

| 类型 | 示例 | 传输 | 持久化 |
|---|---|---|---|
| SSE 事件 | `msg_start`、`token`、`msg_end` | Redis Pub/Sub + Stream | ring buffer |
| 领域事件 | `TurnCompleted`、`UsageRecorded` | Outbox → 队列 | DB outbox |
| 审计事件 | `AgentUpdated`、`ApiKeyRotated` | 同事务/异步 | 审计表 |
| 通知事件 | `TaskFinished`、`ApprovalRequired` | 通知中心 | DB + Redis |
| 集成事件 | `FeishuMessageReceived` | 适配器 → 命令 | 可选 |

### 4.2 SSE 事件契约

```json
{
  "id": "0000000123",
  "event": "token",
  "data": {
    "event_id": "evt_01H...",
    "turn_id": "turn_01H...",
    "message_id": "msg_01H...",
    "seq": 42,
    "version": 1,
    "trace_id": "trace_01H...",
    "delta": "你好"
  }
}
```

**约定**
- `id` 单调递增（每个 message 一条 stream），用于 `Last-Event-ID`。
- `seq` 用于业务顺序/去重；客户端按 `seq` 丢弃重复。
- `version` 用于事件 schema 演进；新增字段可选，删除需升版本。
- 大对象（产物/工具结果）只发引用，不发全文。

### 4.3 事件版本兼容

| 变更 | 兼容性 | 做法 |
|---|---|---|
| 新增可选字段 | 兼容 | 消费者忽略未知字段 |
| 新增枚举值 | 兼容 | 消费者有 default 分支 |
| 字段改名/删除 | 不兼容 | 升 `version`，双发过渡 |
| 语义变化 | 不兼容 | 新事件类型 |

## 5. Outbox / Inbox

### 5.1 为什么需要

消息持久化、用量、审计、通知不能靠「先写 DB 再发消息」保证一致；进程崩溃会丢事件。

### 5.2 Outbox

```
BEGIN
  insert message / usage / audit
  insert outbox(event_type, payload, status=pending)
COMMIT
→ publisher 轮询/CDC 读取 pending
→ 投递到队列/Redis
→ 标记 sent（或 failed + 重试）
```

- 至少一次投递；消费者按 `event_id` 幂等。
- 失败重试 + 死信；管理端可重放。
- 大表按时间分区/归档。

### 5.3 Inbox

- 消费者记录已处理 `event_id`，防重复。
- 处理与业务写入同事务（或幂等 upsert）。

## 6. 工具调用 Saga

工具可能有外部副作用（发飞书、提 MR、写业务系统）。用 Saga 管理：

```
1. 记录 tool_call(pending) + 幂等键
2. 执行工具（超时/取消）
3. 成功 → 记录结果 + 标记 done
4. 失败 → 重试/补偿/标记 failed
5. 需要人工授权 → 暂停 + 发授权提示 + 恢复
```

**补偿**：
- 可逆操作（创建草稿）→ 删除/撤销。
- 不可逆操作（已发消息）→ 记录影响 + 人工处理。
- 补偿本身要幂等。

**恢复**：
- 服务重启后扫描 `pending/running` 超时的 tool_call，标记失败或重试。
- 授权回调用 CAS 把 prompt 从 `granted → consumed`，再重放。

## 7. 取消传播

```
client cancel
→ set cancel flag (Redis + DB)
→ cancel LLM stream (close connection)
→ cancel running tools (SIGTERM/timeout)
→ cancel child agents (cascade)
→ write msg_end(cancelled)
→ release lock
```

**要点**
- 取消是协作式的；工具必须检查取消标记。
- 取消后不再产生新的副作用；已产生的记录保留。
- 取消幂等；重复取消返回同一结果。
- 超时与取消区分：`cancelled_by_user` vs `timeout`。

## 8. 断线续传

```
GET /conversations/{id}/live?message_id=...
Header: Last-Event-ID: 0000000123

1. 解析 active_turn（若无 message_id）
2. 订阅 sse:live:{mid}
3. 重放 sse:log:{mid} 从 Last-Event-ID 之后
4. tail 到 msg_end
5. 若 ring buffer 已截断 → 返回 truncated，客户端拉消息详情补齐
```

**多副本**：任一实例都能服务；Redis Pub/Sub 广播；不依赖本地内存。
**不持 DB 连接**：长连接只读 Redis，避免连接池耗尽。

## 9. 多 Agent 调度

### 9.1 计划模型

```json
{
  "plan_id": "plan_x",
  "version": 2,
  "status": "in_progress",
  "tasks": [
    { "id": "t1", "title": "查 BOM", "status": "done", "depends_on": [] },
    { "id": "t2", "title": "校验采购类型", "status": "running", "depends_on": ["t1"] },
    { "id": "t3", "title": "汇总", "status": "pending", "depends_on": ["t2"] }
  ]
}
```

### 9.2 调度策略

| 策略 | 说明 |
|---|---|
| 串行 | 简单、依赖强 |
| 并行 | 无依赖任务同时跑，受并发/配额限制 |
| 重规划 | 失败/新信息触发，版本 +1 |
| 预算 | 每任务/总任务 token、时长、工具数上限 |
| 公平 | 多用户/多会话按优先级排队 |

### 9.3 失败与死锁

- 依赖失败 → 重试/跳过/升级父 Agent。
- 循环依赖 → 计划校验拒绝。
- 子 Agent 超时 → 父 Agent 收摘要 + 失败原因，决定重规划。
- 总预算耗尽 → 停止并返回部分结果。

### 9.4 上下文隔离

- 子 Agent 独立 `child_session_id`，独立历史。
- 父 Agent 只收「摘要 + 产物引用 + 关键工具结果」。
- 子 Agent 不能直接写父会话；通过事件/结果表回传。

## 10. 关键时序

### 10.1 正常对话

```
Client → API: POST /chat (client_message_id)
API → DB: create turn(pending) + outbox
API → Redis: acquire lock
API → Runtime: start
Runtime → Model: stream
Runtime → Redis: publish token events
API → Client: SSE token...
Runtime → DB: persist message/usage (batch)
Runtime → Redis: publish msg_end
API → Client: msg_end
API → Redis: release lock
```

### 10.2 工具调用

```
Runtime → Model: tool_call
Runtime → DB: tool_call(pending)
Runtime → Tool: execute (timeout)
Tool → Runtime: result
Runtime → DB: tool_call(done)
Runtime → Model: tool result
```

### 10.3 取消

```
Client → API: cancel
API → Redis: cancel flag
Runtime: check flag → abort stream/tools
Runtime → DB: turn(cancelled)
Runtime → Redis: msg_end(cancelled)
API → Client: msg_end
```

## 11. 失败处理矩阵

| 失败点 | 行为 | 恢复 |
|---|---|---|
| 获取锁失败 | 409/排队 | 前端提示/重试 |
| 配额拒绝 | 429 + reset | 等待/切模型 |
| 模型超时 | 重试/备用 | 继续或报错 |
| 工具超时 | 返回超时给模型 | 模型决策 |
| 持久化失败 | 重试/降级 | 从 ring buffer 恢复 |
| 进程崩溃 | turn 标记 failed | 重启扫描/人工重试 |
| Redis 故障 | SSE 降级 | 恢复后重放 |
| 客户端断开 | 保留 ring buffer | 重连续传 |

## 12. 验收标准

- [ ] 同一会话并发请求不会产生两个活跃轮。
- [ ] 取消在 2s 内传播到模型/工具/子 Agent。
- [ ] 断线 30s 重连不丢/不重。
- [ ] 消息、用量、审计通过 outbox 最终一致。
- [ ] 工具副作用有幂等键与补偿策略。
- [ ] 子 Agent 有预算、超时、摘要回传，父上下文不爆。
- [ ] 事件 schema 有版本与兼容策略。
