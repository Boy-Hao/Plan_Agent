# 32 架构治理与演进路线

## 1. 治理目标

- 防止架构腐化：边界清晰、依赖可控、技术债可见。
- 让决策可追溯：为什么这样选、谁批准、何时复核。
- 让演进有节奏：不为未来过度设计，也不被现状锁死。
- 让团队可扩展：新成员能快速理解边界与规则。

---

## 2. 治理机制

| 机制 | 频率 | 产出 |
|---|---|---|
| 架构评审会 | 双周/里程碑 | 评审结论、行动项 |
| ADR 评审 | 按需 | 决策记录 |
| 技术雷达 | 季度 | 采纳/试验/暂缓/淘汰 |
| 架构健康度 | 月度 | 指标/趋势/风险 |
| 故障复盘 | 事件后 | 根因/改进 |
| 容量评审 | 季度 | 扩容/降本 |
| 安全评审 | 季度/变更 | 风险/整改 |

**角色**：架构师（主持）、Tech Lead（提案）、SRE（可运维性）、安全（合规）、产品（价值）。

---

## 3. 架构原则

1. **边界优先**：先定上下文与依赖，再写代码。
2. **契约优先**：API/事件先定，前后端并行。
3. **默认安全**：最小权限、加密、审计。
4. **可逆决策**：优先可回滚/可替换的方案。
5. **可观测**：没有指标的功能不算完成。
6. **渐进演进**：先单体后拆分，先 OBSERVE 后 ENFORCE。
7. **成本自觉**：每个设计说明成本影响。
8. **文档即代码**：ADR/接口/图表随代码评审。

## 4. Fitness Functions

| 函数 | 阈值 | 工具/方式 |
|---|---|---|
| 模块循环依赖 | 0 | import-linter |
| 跨上下文写表 | 0 | 代码扫描/Review |
| 管理接口未鉴权 | 0 | 契约测试 |

**执行**：CI 检查（静态）+ 生产看板（动态）+ 季度评审（人工）。

---

## 5. ADR 流程

```
提案 → 讨论 → 评审 → 接受/拒绝 → 记录 → 复核
```

**模板**
```
# ADR-XXX: 标题
状态：提议/接受/废弃/被取代
背景：问题与约束
决策：选了什么
备选：考虑过什么
理由：为什么
影响：正面/负面/成本
验证：如何验证
相关：文档/Issue
```

**规则**
- 每个重大决策（框架/存储/协议/安全）必须有 ADR。
- ADR 一旦接受，变更需新 ADR 取代，不直接改历史。
- ADR 存 `docs/adr/`，与代码同仓库。

## 6. 技术雷达

| 环 | 含义 | 例子 |
|---|---|---|
| 采纳 | 可用于生产 | FastAPI、MySQL、Redis、React |
| 试验 | 小范围验证 | LangGraph、E2B 自建、OpenSearch |
| 暂缓 | 观望 | 多活、Service Mesh、向量数据库 |
| 淘汰 | 不再新建 | Docker 作为隔离、纯 localStorage token |

**季度更新**：新技术的收益/风险/成本；避免盲目追新。

## 7. 演进阶段

### Stage 1：模块化单体（0–12 月）

```
Control Plane (modular monolith)
  + Runtime (separate process)
  + Worker (async)
  + MySQL/Redis/OSS
```

- 目标：MVP、快速迭代。
- 约束：模块边界、依赖规则、契约。

### Stage 2：拆分 Runtime/Sandbox（12–18 月）

- 触发：Runtime 负载/发布频率/故障隔离。
- 动作：独立部署、独立 DB schema、事件通信。
- 保留：控制面单体。

### Stage 3：拆分 Integration（18–24 月）

- 触发：飞书/GitLab 变更频繁、外部故障影响核心。
- 动作：独立服务、独立队列、熔断隔离。

### Stage 4：拆分 Analytics/Governance（24–36 月）

- 触发：报表压力、审计合规、数据量大。
- 动作：CDC/数仓、独立读模型、审计服务。

### Stage 5：多租户/多地域（按需）

- 触发：SaaS/出海/合规。
- 动作：租户路由、数据驻留、双活。

## 8. 拆分触发条件（量化）

| 信号 | 阈值 | 说明 |
|---|---|---|
| 团队规模 | > 30 人 | 沟通成本 |
| 部署阻塞 | 每周 > 3 次 | 独立发布 |
| 单服务 P95 | > 2× 基线 | 性能隔离 |
| DB 写放大 | > 5k TPS | 分库/拆服务 |
| 故障爆炸半径 | 单模块影响 > 30% 用户 | 隔离 |
| 变更频率 | 每周 > 2 次 | 独立节奏 |
| 合规要求 | 数据隔离 | 独立部署 |

**拆分前先做接缝**：接口、事件、独立 schema、Feature Flag；不要「大爆炸」重写。

## 9. 团队拓扑与所有权

| 团队 | 所有权 | 接口 |
|---|---|---|
| Agent & Chat | Agent/Chat 上下文 | 对内 API |
| AI Platform | Runtime/Model Gateway | 模型网关 API |
| Execution | Sandbox | 任务 API |
| Integrations | 飞书/GitLab/A2A | 适配器 API |
| Trust | Identity/Governance | 权限/审计 API |
| Web | 前端 | BFF/API |
| SRE | 基础设施 | 平台能力 |

**规则**：每个服务/表有 Owner；跨团队变更走接口/ADR；共享库由 Platform 维护。

## 10. 36 个月路线

| 时间 | 重点 | 里程碑 |

## 11. 架构健康度看板

- 依赖图（模块/服务）
- 循环依赖数
- API 契约变更数
- 技术债（TODO/漏洞/过期依赖）
- 变更失败率/回滚率
- 故障数/MTTR
- 成本趋势
- SLO 达成率
